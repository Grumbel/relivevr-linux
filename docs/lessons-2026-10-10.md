# Lessons learned — 2026-10-10 (Present / ptsSensor / decoder)

This session chased black/green screens, `Pose for Present pts=… not found`,
`input frame sensor pts not found … prev=0`, decoder lag, and “Slow network”
on Daydream + ReliveVR Linux server. Evidence sources: **dumpsmall.pcapng**
(Windows capture), **com.amd.wirelessgvr APK** (`libwirelessvr-lib.so`), and
repeated Android logcat.

Related docs: [windows-pcap.md](windows-pcap.md), [client-apk.md](client-apk.md),
[protocol.md](protocol.md).

---

## 1. What the Windows dump actually sends

### Session order (server → client unless noted)

1. Discovery / Hello / HelloResponse  
2. StartRequest (client) with display + codec prefs  
3. TrackableDeviceCaps (ctrl), then **VideoInit** (JSON + HEVC VPS/SPS/PPS trailer)  
4. **StartSensor**  
5. Continuous **DeviceEvents** (`/hmd/pose`, `/ctrlRight/pose`, inputs…)  
6. Continuous **VideoData** (JSON + Annex-B NALs) on FlowCtrl channel 1  
7. Occasional client `{"FrameRate":…}` (~72–75 later in the capture)

### VideoData body (OnFrameReceived type byte = `1`)

```
[0x01][JSON NUL-terminated][Annex-B NALs…]
```

JSON fields (order as in dumpsmall):

| Field | Windows behaviour |
|-------|-------------------|
| `frameNum` | Increments per stereo pair |
| `frmType` | `0` left, `1` right (same `frameNum` / `pts` / `ptsSensor`) |
| `encType` | `0` IDR, `2` P |
| `pts` | Early: ≈ `frameNum * 166666` (60 Hz in 100 ns units). Later steps change with client FrameRate (~72/75) |
| `ptsSensor` | **Exact** `/hmd/pose` sample `time` (~1e16). **Never** controller times (624/624 in dumpsmall) |
| `ptsSend` | Small (0…~6700), **not** equal to `pts` |
| `ptsEncoderLat` / `ptsServerLat` | Large µs-scale pipeline latencies |
| `cmpFrmSize` | Compressed AU size |

### Pose timing before video

- ~**43** `/hmd/pose` samples (and ~85 total pose timestamps) exist **before** the
  first VideoData `ptsSensor`.
- Frame 0 already has a real non-zero `ptsSensor` (poses flowed after StartSensor).
- Windows does **not** emit one-shot VideoData with `ptsSensor=0` or a leftover
  `pts=16666`-style path.

### Wire packaging

- One FlowCtrl datagram up to ~MaxDatagramSize (~65 KB), IP-fragmented on the wire.
- Splitting into small (~1400 B) FlowCtrl fragments produced solid green on the
  Daydream in earlier experiments.

## 2. What the client APK does with those fields

Library: `libwirelessvr-lib.so` (arm64).

### Present lookup (exact match, not nearest)

```
OnFrameReceived(VideoData)
  → map[pts] = ptsSensor     (insert; left-eye path registers the pair)

Motor::GetHeadPoseByPresentTime(present_pts)
  → sensor = map[present_pts]   // exact; entry is consumed (one-shot)
  → pose   = queue[sensor]      // exact match on Pose.time
```

Symbols (arm64 VA):

| Function | VA |
|----------|-----|
| `Motor::OnFrameReceived` | `0xdc388` |
| `Motor::AddHeadPose` | `0xdbb04` |
| `Motor::GetSensorTimeFromPresentTime` | `0xe028c` |
| `Motor::GetHeadPoseByPresentTime` | `0xe037c` |
| `Motor::QueryAndSendSensors` | `0xd91c4` |
| `Motor::SensorThread::Run` | `0xd8f94` |

### Same time on wire and in the local queue

`QueryAndSendSensors`:

1. Sample HMD → `SensorEngine::Pose`  
2. `AddHeadPose(pose)` — local Present queue (`Pose.time` at +104 → node +120)  
3. `DeviceEvent::AddValue("/hmd/pose", pose, time)` — **same** `time` on the wire  

So echoing `/hmd/pose` `time` as `ptsSensor` is correct **if**:

- the sample is still in the pose queue when Present runs, and  
- the value is truly an HMD time (not a controller time).

### Failure modes (logcat)

| Message | Meaning |
|---------|---------|
| `input frame sensor pts not found … prev=0` | Sensor-time lookup failed (wrong domain or aged out); `prev=0` = no prior hit |
| `Pose for Present pts=N not found, queue size: …` | Present could not resolve pose for that `pts` (map miss and/or pose-queue miss); queue size grows when Present keeps failing |
| `Slow network!!! Time since last message N ms` | Gap since last relevant message; N≈80 ms ⇒ ~12 fps effective |
| `Decoder lag … excess … ms, lagging N frames` | Decode behind presentation timeline |
| `Video Decoder input is full` | MediaCodec input buffers saturated |
| `qcom.decoder.avc` + OMX `UnsupportedSetting` | Common Qualcomm noise; surfaces can still init |

## 3. Root causes we confirmed (not guesses)

### A. Controller times as `ptsSensor` (fixed)

DeviceEvents carry both `/hmd/pose` and `/ctrlRight/pose` with **different**
`time` values. If the server’s `latest_time` was updated from **any** pose
event, `ptsSensor` could be a controller time. The client pose queue is **HMD
only** → exact match fails → `sensor pts not found … prev=0`.

**Fix (085.1):** only `/hmd/pose` updates `latest_time` / `ptsSensor`.

### B. Stale render-time stamp under lag (mitigated)

APK match is exact. Under 80–300 ms encode/network lag, a pose stamped only at
**render** may have left the client queue before Present.

**Fix (087.1):** at UDP send, prefer the **freshest** HMD `latest_time`; fall
back to the render stamp. Still HMD-only.

### C. Video before the pose queue is warm (mitigated)

dumpsmall has dozens of HMD poses before first video.

**Fix (089.1):** do not emit VideoData until ≥30 `/hmd/pose` samples received.

### D. One-shot / zero `ptsSensor` frames (removed earlier)

Early Linux paths sent one-shot IDR/P with `ptsSensor=0` or odd `pts` (e.g.
16666). dumpsmall never does that; Present stalled on `pts=0` with an empty map.

### E. `ptsSend = pts` (removed earlier)

Windows `ptsSend` is a small latency counter. Setting it equal to large `pts`
does not match the dump.

### F. Decoder backlog (still open as of tip 090.1)

After pose-binding warnings largely disappeared from logcat, remaining symptoms
were:

- ~80 ms inter-message gaps (“Slow network”)  
- Decoder lag climbing hundreds of ms  
- MediaCodec input full  

That is a **throughput / encode / network** problem, not another Present field
tweak. Windows path is hardware-friendly (HEVC-oriented dump, steady 60 fps).
Linux soft AVC (openh264/x264) at 1440² stereo often cannot sustain the same
pipeline on Daydream’s `qcom.decoder.avc`.

**Mitigations tried (090.1):** ~60 fps send throttle (16 ms min interval);
prepend SPS/PPS on IDR if the AU lacks them.

## 4. What did **not** work / dead ends

- Arbitrary PTS multipliers without dump evidence.  
- “Nearest pose” assumptions — client uses **equality**.  
- Treating controller poses as valid `ptsSensor`.  
- One-shot video bursts to “kick” the decoder.  
- Small FlowCtrl MTU splits (~1400 B) → solid green historically.  
- Expecting more `pts`/`ptsSensor` JSON edits alone to fix **decoder full** after
  Present warnings were gone.

## 5. Server implementation contract (Linux tip line)

| Requirement | Implementation direction |
|-------------|---------------------------|
| `pts` | `frameNum * 166666` early (60 Hz, 100 ns units) |
| `ptsSensor` | Exact `/hmd/pose` `time` only; freshest at send preferred |
| `ptsSend` | Small latency (0 or measured µs), not equal to `pts` |
| Stereo | Same `frameNum` / `pts` / `ptsSensor` for left then right |
| Before first video | ≥30 HMD poses (warm client queue) |
| Body | `0x01` + JSON + `NUL` + Annex-B |
| FlowCtrl | Large max payload (~65 KB), not tiny fragments |
| IDR | `encType=0`; ensure SPS/PPS via VideoInit and/or in-band |
| Rate | Aim ~60 fps; do not flood MediaCodec |

Code touchpoints: `src/pose.rs` (`latest_time`, `hmd_sensor_time`),
`src/viz.rs` (stamp at publish), `src/main.rs` (send path, warm-up, throttle,
VideoData JSON).

## 7. How to test / what to look for

```bash
RELIVEVR_VIZ=1 RELIVEVR_ENCODER=openh264 cargo run
# or x264 / hevc backends as available
```

**Server log**

- `waiting for HMD pose queue warm-up (n/30)` then  
- `live frame #0 … pts=0 ptsSensor=<large> … (hmd_poses≥30)`  
- `ptsSensor` must stay non-zero; `hmd_poses` must climb  

**Client logcat (progress)**

- Absence of `sensor pts not found` / `Present pts=… not found` → pose path OK  
- Presence of `Decoder lag` / `input is full` / `Slow network` → encode/network path  

**Next evidence if still broken**

1. Linux **pcap** of a failing session next to logcat (frame size, inter-arrival, loss).  
2. Lower resolution / bitrate / fps and retest.  
3. Prefer HEVC if the client accepts it (closer to Windows dump).  
4. Compare openh264 vs x264 vs hardware encode on the same network.

---

## 8. One-line summary

**`ptsSensor` must be an exact live `/hmd/pose` time still in the client’s pose
queue; Present maps `pts → ptsSensor → pose` by equality. After that is correct,
remaining black/green + lag is decoder/network throughput, not more PTS
guesswork.**
